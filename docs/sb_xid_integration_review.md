## 手法の理解と論文との違い

SB-XIDは、正常値・故障値を論理シミュレーションで求め、検出POからPATHとJUSTIFYを抽出する。その範囲に「元の論理値を固定する必要があるか」を表す変数を割り当てる。内部信号には正常側と故障側の別変数を用意し、PIでは同じ変数を共有する。この変数は実際の0/1信号値とは異なる。

故障点の固定、検出POの選択、経路の後方含意、ゲート値の正当化を擬似ブール制約で表す。PIの固定数を小さくし、同点では内部信号の固定数を大きくする目的関数をclaspで最適化する。固定が必要とされたPIだけ元の0/1値を残し、他をXにする。最後に3値故障シミュレーションで検証する。

| 論点 | 論文 | 同梱v1ソース |
|---|---|---|
| 再求解 | CEGARで制約を追加し反復する | 1回求解して検証する。CEGARなしと明記（9–17、1167–1172行） |
| 検証失敗 | 反例に基づいて補修する | NOT-Detectedを記録し、その候補も出力する（1456–1478行） |
| 非制御値の正当化 | オフパス入力を個別固定し、伝搬入力群は少なくとも1本を固定 | `CreateConsEss_StandardGate()` は変数のある全入力を個別固定する（634–640行） |
| 故障数 | 1故障と1パターン | 単一版と複数故障版がある。バッチは複数故障版を呼ぶ |

今回の基準は同梱v1であり、CEGARや論文の正当化規則を追加して合わせることはしない。論文の「LOSSなし」「平均6.8倍」等の実験結果を、この版やFDP列挙にそのまま適用することもできない。最適解とは生成したPBOモデル内での最適性であり、任意の健全キューブ全体でX数最大になる保証とは区別する。

## 現行プログラムへの接続

接続位置は `src/fdp/fault_detection_prob.c:124` の `InlineXID()`。現在は次の処理になっている。

```text
CaDiCaLで検出パターンを生成
  → XIDでキューブ化
  → キューブを禁止する節をCaDiCaLへ追加
  → CubeSetへ保存
  → 列挙後にBDDで和集合のFDPを算出
```

このXIDの部分を、次の処理へ置換する。

```text
SATモデルから元の0/1パターンを取り出す
  → SB-XIDの故障シミュレーションとPATH/JUSTIFY抽出
  → 元の式に基づくOPB生成とclaspライブラリによる最適化
  → 候補キューブを必ず検証
  → 成功なら候補、検証失敗なら元の0/1パターンを返す
```

禁止節・CubeSet・BDDの間の受け渡しは、全PIについて `pi[]` 順の `0/1/X` 文字列とする。SB-XIDの出力記号 `-` は接続部で `X` に変換する。返却文字列はC側で解放できる所有権に統一する。

今回の用途は1故障ごとのFDPなので、同梱バッチ版の `build_multi_case()` / `generate_opb_for_multi_bundle()` を故障数K=1で使う案を勧める。配布版のバッチ処理と同じ経路を参照でき、複数故障の機能を新たに利用者へ追加する必要はない。

## 元コードを保つための構成

**CのSB-XIDコア、Cの接続部、C++のclasp接続部を分ける。** `SB-XID/` の参照ソースを保持し、移植コードは例えば `src/fdp/sbxid/` に置く。元コードと移植コードの対応・必要な差分を記録する。

| 部分 | 方針 |
|---|---|
| 3値シミュレーション、PATH/JUSTIFY抽出 | 元の処理を利用する |
| OPBの式、目的関数、変数対応 | 元のバッチ版をK=1で利用する |
| `main()`、対話入力、バッチファイル入出力 | ライブラリの経路から外す |
| `.\\clasp.exe` の `system()` 呼び出し | C++ライブラリ接続へ置換する |
| `clasp_out.txt` の解析 | ライブラリの最終モデル、目的値、終了状態の取得へ置換する |
| ネットリスト読込 | 本体が読んだ回路からSB-XID用の表現を作る |
| 検証の条件付き実行 | ログ・出力設定によらず最終候補を検証する |

最初はOPBのテキスト形式を残し、メモリ上のOPBをclaspの公式パーサへ渡す。これなら `fprintf()` で書かれた制約式を大幅に変更せず、プロセス起動とディスク上のOPB・結果ファイルをなくせる。全制約をPBBuilderへ直接追加する方式は、初期導入の後に必要性を判断する。

OPB生成関数のファイルを開閉する部分を、呼出側が用意するストリームへ出力する形に切り出す必要がある。Linux / WSL2では `open_memstream()` 等が候補。元コードは最後に先頭へシークしてヘッダを書き直すため、メモリストリームでは本文を含む全長が保持されるよう末尾へ戻す処理も必要。ヘッダの変数数・制約数、本文、負の係数が同じであることを比較する。

clasp接続は `ClaspFacade` とOPBパーサを使い、元と同じ `--opt-heuristic=model --opt-mode=opt` 相当を設定する。C++の公開境界は `extern "C"` にし、例外をC側へ通さず状態として返す。最初のSATモデルだけで止めず、最適化の終了と最終モデルを取得する。

## 互換性で注意する点

1. **ネットリスト構造体を直接共有しない。** ゲート種別の数値や名前・接続の基本項目は共通だが、現行NLISTにはSAT用変数等があり、SB-XIDには `value` / `signal` / `target` 等がある。項目の順序も異なる。ポインタの型変換で兼用できない。
2. **SB-XIDの作業フラグの扱いを決める。** 本体のFP/TFO/TPOと、SB-XIDのEVALUATED/PATH/JUSTIFYは同じビットを別の意味で使う。`clear_all_flags()` は本体のフラグも消す。専用フィールド・専用回路を使う案と、呼出側で保存・復元して共用する案がある。現行処理はXID呼出し後に本体フラグを参照しないため、回路全体の複製が唯一の解決策ではない。
3. **名前とIDを保つ。** 新しくVerilogを読み直さず、本体が分岐・幹を展開した回路から変換する。PI順と故障点IDを明示的に対応させる。`nl` / `pi` / `po` 等のグローバルとキュー関数はSB-XID側で名前を分ける。
4. **故障種別を変換する。** 本体のSF0/SF1は8/16、SB-XIDは0/1。対象故障の構造体から明示的に変換する。
5. **正常CNFの範囲限定を維持する。** 保持範囲内PIはSAT値を取り出し、範囲外PIは0で補完して元の完全パターンを作る。未投入の内部SAT変数を読む代わりに、SB-XIDの論理シミュレーションを行う。返却キューブも全PIの順序と長さを守る。
6. **プロセス並列とclasp内部並列を重ねない。** 当初はclaspを1スレッドで使う。claspのコンテキストはfork後に作り、各ワーカー内で所有する。PBOモデルはパターンごとに新規構築し、前の目的関数・探索状態を持ち越さない。
7. **現在扱っている回路を試験する。** AND/NAND/OR/NOR/BUF/FOUT/INV、XOR/XNOR、PI・枝・幹の故障、複数PO、回路から切り離されたPI、全Xキューブ、擬似PI/POを含める。DFFを生の順序回路として扱う設計は今回追加せず、現行の組合せ部分の扱いを確認する。

単一版の目的関数はPI重みが `n_net+1`（738行付近）、複数故障版は `(K+1)*n_net+1`（938行）。内部変数は正常・故障側の両方が数えられるため、両版を無条件に同じ重み付けとして扱わない。K=1のバッチ版を採用し、この係数自体は移植時に変更しない。

## 状態と検証失敗の扱い

| 状態 | FDP側の処理 |
|---|---|
| 最適解を取得し、候補が検証を通過 | 候補をキューブとして採用 |
| 候補がNOT-Detected | 元の検出済み0/1パターンを採用し、検証失敗・フォールバックを計数 |
| 最適性未証明だがモデルあり | SAT(OPT)と区別する。採用する場合も検証が必須。初期の通常実行では求解上限を設けず最適化完了まで待つ |
| PBOのUNSAT、UNKNOWN、パース失敗、資源不足 | 想定外の状態としてエラーを返す。対象故障を冗長と判定せず、不正な候補の禁止節・BDD結果を作らない |
| 元の0/1パターン自体が検出しない | 接続またはモデルの不整合としてエラー停止 |

CaDiCaLの列挙終了UNSATと、SB-XIDのPBOモデルのUNSATは意味が異なる。検証失敗のフォールバックはユーザーと合意済みだが、ソルバ起動・入力等の異常を隠すフォールバックとは分ける。

ログには方式・clasp版・最適化時間・検証失敗件数・フォールバック件数を記録する。通常のCSVの列構成を維持し、研究上の比較ではフォールバックによるキューブを区別できるようにする。

## claspの用意：Linux / WSL2

WSL2ならLinux側のシェルで実行する。Windows用の同梱exeを使う必要はない。以下はリポジトリのルートで、`external/clasp` がまだ存在しない初回向けの手順。

```bash
sudo apt update
sudo apt install -y build-essential cmake git

git clone --depth 1 --branch v3.3.9 \
  --recurse-submodules --shallow-submodules \
  https://github.com/potassco/clasp.git external/clasp

cmake -S external/clasp -B build/clasp \
  -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_SHARED_LIBS=OFF \
  -DCLASP_BUILD_APP=ON \
  -DCLASP_BUILD_EXAMPLES=ON \
  -DCLASP_BUILD_TESTS=OFF \
  -DCLASP_BUILD_WITH_THREADS=ON \
  -DCLASP_INSTALL_LIB=ON \
  -DCMAKE_INSTALL_PREFIX="$PWD/build/clasp-install"

cmake --build build/clasp --parallel 2
cmake --install build/clasp

build/clasp/bin/clasp --version
build/clasp/bin/clasp_examples
```

`--recurse-submodules` で依存のlibpotasscoも取得する。`CLASP_INSTALL_LIB=ON` はヘッダ・ライブラリ・CMake設定ファイルをインストールするために必要。インストール先をリポジトリ内にしているので、インストールにsudoは不要。exeとサンプルは導入確認用であり、本体の実行時にはライブラリを使う。

追加の設計更新：各claspの求解を1秒で打ち切る方針を受け、上記のCLASP_BUILD_WITH_THREADSをONへ更新した。公式の非同期求解APIで待機時間を制限し、cancel()で停止する案に必要となる。各worker内の探索自体は1スレッドにする。以前の依存単体・接続試験はOFFで行ったもので、非同期の時間制限経路は本体移植時に別途確認する。

CMake 4.xで古いポリシーの互換性エラーが出る場合は、上の構成コマンドへ `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` を追加する。今回確認したCMakeは3.31.6。

生成物は `build/clasp-install/include/clasp/`、`include/potassco/`、`lib/libclasp.a`、`lib/libpotassco.a`、`lib/cmake/Clasp/` 等。`clasp/config.h` はビルド時生成物なので、ソースのヘッダだけをコピーしない。

後の本体CMake変更ではCとC++の両言語を有効にし、C++の接続部だけをC++としてコンパイルする。既存Cファイルを一括でC++へ変えない。ライブラリは公式のCMake設定を使って次の形でリンクできる。

```cmake
find_package(Clasp CONFIG REQUIRED)
target_link_libraries(sbxid_solver PRIVATE libclasp)
```

`sbxid_solver` は今後用意する接続部のターゲット名の例。本体の構成時に `-DCMAKE_PREFIX_PATH="$PWD/build/clasp-install"` を渡す。`libclasp` ターゲットがlibpotasscoへのリンクと必要なインクルードを伝える。現時点の本体CMakeはまだこの変更を含まない。

固定するソースはclasp v3.3.9（`4c708a73fdcb78049e9c3bad863a3f6eab437a07`）、対応するlibpotassco（`fa39da44cf9643e1b56389d3dfed6af773305af3`）。同梱exeにも3.3.9のバージョン文字列がある。3.4.1も依存単体のビルドとサンプル実行を確認したが、初期導入は3.3.9を基準にする。

## 今回済ませた検証と、実装時の検証

今回、一時ディレクトリでGCC/G++ 14.2とCMake 3.31.6を使い、次を確認した。

- clasp 3.3.9と対応libpotasscoのビルド・ローカルインストール。
- `clasp --version`、公式の4種類のライブラリサンプルの実行。
- 別の小さなCMakeプロジェクトから `find_package(Clasp)` / `libclasp` で接続できること。
- メモリ上のOPBに対して、負の係数・目的関数・行末コメントを読めること。
- 元コードと同じ最適化オプションで、既知の最適値10、最適性証明、元の変数番号によるモデル取得を確認。
- 別の矛盾したOPBで、UNSATを最適解と区別できること。

これは依存・接続方式の検証であり、SB-XIDを本体へ統合した結果の正しさや性能を検証したものではない。

実装時は次の順で進める。

1. **元コードとの照合。** 同じ回路・完全パターン・故障について、PATH/JUSTIFY、変数対応、生成OPBを比べる。同じclasp版・オプションを使い、最適値、ケア数、検出性を照合する。同点解が複数ある場合、キューブ文字列の一致だけを必須条件にしない。
2. **各キューブの健全性。** 小回路ではXの全具体化を独立にシミュレーションし、どの具体化でも対象故障を検出することを確認する。大きい回路では独立の検出関数を用いた `cube AND NOT detection` のUNSAT照合を利用する。SB-XID自身の検証だけに依存しない。
3. **既存FDP回帰。** c17aの36行の `net_name,f_type,fdp` を既知値と照合し、無制限実行の `complete=1` を確認する。s27_C等も完全列挙で照合する。キューブ数の一致は要求しない。
4. **失敗経路。** 検証失敗で元の0/1パターンへ戻ること、そのパターンが正しく禁止されること、計数されることを確認する。UNKNOWN・入力異常等を無検出や正常完了へ変換しない。
5. **既存の最適化との組合せ。** 正常CNFの範囲限定、支配関係による流用のon/off、EA、jobs=1と複数プロセスを確認する。プロセス間のCSV順序と完全FDPを維持する。
6. **性能評価。** 同じ条件で総経過時間、CaDiCaL時間、SB-XID最適化・検証時間、キューブ数、X数、完了故障数、部分FDP、メモリ、失敗・フォールバック件数を比べる。まず小回路、次にs5378_Cなどへ進む。

完全列挙のFDPは方式によらず同じ値になるべき。一方、上限付き実行の部分FDPや完了故障集合は変わりうる。X数が増えても、最適化の計算時間が加わるため、全体の高速化は実測して判断する。

今回の検討に必要な選択は回答済み。次の実装で確認すべき点は、回路変換・元OPBとの同値性・健全性・性能であり、同梱v1のアルゴリズムを変更する理由が出た場合は、その差分を先に検討する。
