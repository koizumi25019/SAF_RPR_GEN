# 故障単位の並列化の実現可能性

調査日: 2026-10-04。本体未統合。ユーザー提示のFFR単位のworkerコードを参考に、
現行SAT/XID/生成被覆BDDパイプラインの独立故障処理を調べた。
ユーザーの方針は「効果が小さければキューブ流用をなくして単純にする」。

CNF・XIDの具体的な競合例、常駐プロセス/スレッド/段階分割の比較と推奨構成は
[DESIGN.md](DESIGN.md)を参照。画像のスレッド方式に限定せず、各workerが一故障の全処理を行う
常駐プロセスプールを本体向け第一候補とした。今回追加したのは設計検討で、常駐方式の性能は未測定。

## 実測結果

s5378_C・SAF・limit30・全4,551代表故障、Release、2回の中央値。
並列試験ではキューブ流用なし。36バッチの外部プロセス実行で、起動・待機時間も含む。
環境はi7-13700Kと表示されるWSL2 VM、16論理CPU（VM上の表示は8コア×2スレッド）、メモリ約27 GiB。
ホスト全体の他の負荷は管理しておらず、物理コア数や他環境の倍率を保証しない。

| 条件 | 経過時間の中央値 | 同じバッチ方式の1並列に対する倍率 |
|---|---:|---:|
| 既存の直列・流用あり | 53.311秒 | 比較用 |
| 全件一プロセス・流用なし | 54.186秒 | 比較用 |
| 1並列・流用なし | 53.061秒 | 1.00× |
| 2並列・流用なし | 26.291秒 | 2.02× |
| 4並列・流用なし | 13.486秒 | 3.93× |
| 8並列・流用なし | 8.264秒 | 6.42× |

流用を止めた直列全件の増加は**約1.64%**。既存の流用あり直列から8並列への総時間倍率も約6.45倍だった。
流用ありでは105,977キューブ中7,686本がseedで、新規生成は98,291本。
流用なしでは100,982本を新規生成した。seed数の7.3%をそのまま時間短縮率として扱えない。
また本数上限があるので、流用なしの総被覆キューブ数が少ないことを完全列挙の改善と解釈しない。

2回それぞれの8並列は8.268秒・8.259秒、4並列は13.502秒・13.470秒。
全1/2/4/8並列・両反復で、各代表故障の`fdp/complete/cube_cnt/seeded_cnt`が流用なし直列と一致した。
比較では全代表故障の重複・欠落がないことも検査した。
並列数を増やしても出力する代表被覆の内容は変わっていない。
生値・各子プロセスの時間・RSSは`results/benchmark.json`に保存した。

流用あり→なしでは、完了数は1,571→1,567、完了→未完了が5件、未完了→完了が1件。
両方で完了する1,566件のFDPはすべて一致した。FDP値が変わった代表行は83件。
この差は並列化による差ではなく、流用を止めてlimit30の部分被覆が変わることによる差である。
詳細は`results/dependencies.json`に保存した。

各バッチの最大RSSは最大25,300 KiB（約24.7 MiB）。これは子一つの最大値で、プロセス群全体の同時最大RSSではない。
8並列の子プロセスの経過秒の合計は約59〜60秒、1〜4並列では約53秒であり、
並列実行中に個々の処理が遅くなる効果も見えている。経過秒の合計をCPU時間とは呼ばない。
この条件では8並列まで大きく短縮できたが、論理CPU数に比例する16倍の保証にはならない。

## 正しさの検証

- c17aの無制限実行: 全CSV行の`net_name/f_type/fdp`が`expected/c17a_result.csv`と一致。
- c17aの流用なし・4並列バッチ: 全代表故障のFDPが上記結果と一致し、全バッチGT ALL VERIFIED。
- s5378_Cの流用なし・8並列バッチ: 36バッチ、合計4,551代表故障すべてGT ALL VERIFIED。
  完了1,567件は検出集合との等価性、未完了2,984件は被覆の健全性を検査した。
  GT検証を有効にしても、代表行は流用なし直列と完全一致した。
- 元の`src/`全ファイルは、実験開始時のSHA256と終了時で一致。

GTは独立検証のみに使い、求解や厳密化フォールバックには使わなかった。
性能表にはGT検証実行を含めない。全故障の厳密FDPを完了した性能表ではない。

## 依存と処理時間の分布

現行の支配流用グラフは353辺、依存を持つ故障は124件（2.7%）。
弱連結成分は4,198個で、最大成分は5故障。独立な単一故障成分は4,074個だった。
流用を維持する設計も可能だが、この条件で約1.6%の時間効果を得るために依存管理を残す理由は弱い。

既存直列・流用ありの初回測定では、故障区間の合計52.817秒、最長故障は約0.054秒。
このlimit30条件では、特定の一故障が終了を長時間待たせる分布ではなかった。
固定した故障時間を使う理想workerの依存ready queueシミュレーションでは、
4workerは13.210秒、8workerは6.610秒。これは速度低下・出力・起動・初期化等を省いたモデルで、実測値ではない。
結果と仮定は`analyze.py`、`results/dependencies.json`に保存した。

## 設計の結論

現行の自然な仕事単位は**代表故障一つ**である。FFRへの分割は並列化の必須条件ではない。
`AnalyzeFaultDensity` は故障ごとにCaDiCaLを新規作成し、禁止節・生成キューブも故障ごとに持つ。
各故障の厳密FDPはその故障の検出集合だけで決まるため、故障間の処理順は数学的には不要。
等価故障の代表化とCSVへの展開は維持する。支配関係によるキューブ流用とは別の機能である。

今回の測定条件では流用の時間効果が小さく、**流用をなくした独立故障の動的配分**を第一候補にする。
まず別プロセスでの並列化が実装しやすい。現在のグローバルな可変状態をプロセスごとに隔離できるためである。
スレッド版に進む場合は、可変状態をworker contextへ移す設計が必要になる。
故障ごとに新プロセスを起動する方式ではなく、常駐workerへ仕事を配る方式が本体向けの候補。
今回の試験は、複数故障をまとめた外部プロセスを動的に起動するバッチ実験であり、常駐workerの実装ではない。

## 本体コードで確認した制約

| 対象 | 現行実装 | 並列化時の扱い |
|---|---|---|
| CaDiCaL | `fault_detection_prob.c`で故障ごとにinit/release | 独立solverを維持 |
| 正常回路・正常CNF | `nl[].in/out/type`、`consgc`、`varsgc` | 準備後は読み取り専用で共有可能 |
| 故障CNF | `SearchTFO`が`nl[].flag/varsfc/varprop`と`cnf`を書き換える | workerごとの状態へ分離 |
| EssentialAssignment | `nl[].logic_value/ea_flag/unique_flag`を書き換える | workerごとの状態へ分離 |
| XID | `XID.c`のstatic状態配列・キュー、`xid_adapter.c`のレベルスタック | workerごとの作業領域。関数表は開始前に一度初期化 |
| BDD | 全故障で一つの`DdManager`を使用 | プロセスごとに独立、またはスレッド版ではworkerごと/集約側一つ |
| GMP | 毎回`mpf_set_default_prec(8192)`→`mpf_init` | スレッド版では開始前に設定、または`mpf_init2`へ変更 |
| 対象選択 | `SetTarget`が毎回全故障を走査 | 代表故障配列を一度作り、未処理indexを配る |
| CSV・ログ | 共有FILEへの書き込みと集計 | 集約側で一度出力、安定した順番・header・等価故障展開を管理 |
| 実験フック | `experiment.c`、`gt_verify.c`、`pcount.c`等にstatic状態 | プロセスでは隔離可能。スレッド版では個別のcontext化が必要 |
| 計時 | 本体の区間計測が`clock()` | スレッド版ではthread CPU時計/経過時計を使用。`clock()`はプロセス全体 |

画像の`fetch_add(1)`方式は、上記の隔離を済ませた後の仕事配分に利用できる。
`next_index`だけをatomicにしても、CNF生成やXIDの競合は解消しない。
また、画像に写っていない`generate_condition`の内部状態や実測性能は判断できない。

CUDD 3.0.0の同梱`external/cudd/RELEASE.NOTES`は、OOMハンドラを変更しない条件で
異なるmanagerを別threadで実行できると記述している。CUDD自体を理由にスレッド並列化を却下する必要はない。
一つのmanagerを無同期で共有する設計は採らない。
GMPのデフォルト精度はグローバル状態であることも[公式マニュアル](https://gmplib.org/manual/Reentrancy.html)で確認した。
limit30の既存計測ではBDD費用が小さいため、SAT/XIDをworkerで実行してBDDを集約側に置く設計も候補になる。

`DropDeteFault`は現行コードでは今回の対象だけを処理済みにする。
別故障をキューブでシミュレーションして落とす実装にはなっていない。

## キューブ流用をなくす意味

`MDC_NODOM=1`は既存の流用停止スイッチであり、故障ごとの独立列挙を試せる。
ただし支配関係の構築、`n_pending`の減算、キューブ保持自体は残るため、今回の数値はそれらを削除した完成版の数値ではない。
本体で流用をなくすなら、支配グラフ構築・seed追加・参照カウント・後続故障用の被覆保持をまとめて不要にできる。
等価故障の代表化は残す。

完全列挙が終われば流用の有無で厳密FDPは変わらない。一方、`-limit 30`ではseedも上限に含まれ、
SATの禁止節と解順が変わるので、部分被覆・下界FDP・完了する故障の集合が変わり得る。
流用なし直列との一致と、流用あり既存結果との一致は区別する。

## 実験の範囲と再現方法

本体`src/`を`build/source/`へコピーし、Releaseでビルドした。
変更したコピーには代表故障・支配辺の書き出しと、故障単位の経過時計だけを加えた。
本体`src/`、既存`build/`、`output/`は変更しない。
入力・生成ログ・生成CSVは`runs/`、集計JSONは`results/`に保存する。
コピー前の全ソースSHA256は`build/source_hashes.json`に保存する。

対象はSAFのs5378_C、全4,551代表故障、limit30、cube_analysisなし。
流用あり/なしの直列全件実行と、流用なしの1/2/4/8並列バッチ実行を比較する。
レベル順に並べた故障をround-robinで36バッチに分け、各バッチ最大127件とする。
PythonのThreadPoolExecutorは外部プロセスの起動と待機だけを行い、求解は各C実行体が行う。
同じ比較を2回行い、2回目は並列数の実行順を逆にする。他の本実験を同時に走らせない。
これは単一マシンの探索的測定で、一般的な性能保証ではない。

明示的な`-fault`指定では本体の自動等価故障解析が実行されないので、
バッチCSVのエコー行を単純連結して本体出力として採用しない。
実験の比較は`complete`が空でない代表行のみを使い、全代表故障の重複・欠落がないことを検査する。
本体実装では代表化を全体で一度実行し、同じ等価故障対応を集約側で使う必要がある。

```bash
python3 verification/parallel_feasibility/build.py
python3 verification/parallel_feasibility/run.py --repeats 2
python3 verification/parallel_feasibility/analyze.py
```

## 高速化の限界と次の判断

故障コストを`t_i`、worker数を`p`とすると、独立故障処理の経過時間の下界は
`max(sum(t_i)/p, max(t_i))`である。初期処理、出力、配分費用、並列実行中の各故障の速度低下はこれに加わる。
完全列挙で一件が全時間の大半を占める場合、その一件を分割しない故障並列化の効果は小さい。
平坦キューブ被覆の指数的な増殖そのものは、故障を並列に処理するだけでは解決しない。

同じ故障内のキューブを単純に複数solverへ配ると、禁止節の共有・重複・完了判定が別問題になる。
最初は故障間だけを並列化する。同数故障の静的割当てより、空いたworkerへ次の故障を配る方式を優先する。
1/2/4/8 workerを比較してCPU資源に合う設定を選ぶ。論理CPU数をそのまま倍率として扱わない。
メモリはsolver・XID・BDDがworker数ぶん増えるため、大回路・full・BDD_EXACTの条件を別に測る。
XIDのレベルスタックは各レベルに`n_net`個のpointerを確保するので、確保容量と実RSSを区別する。

TDFはもともと支配流用がなく、独立故障配分に向いている。
今回の実測はSAF/limit30だけであり、TDF/full/MAXDC/PCOUNT/BDD_EXACTの速度や正しさを今回確認したとは主張しない。
本体へ統合する際は、c17ゴールデン、既存GT_BDD回帰、TDFの励起とPPO観測、limit付きの健全性を検証する。
