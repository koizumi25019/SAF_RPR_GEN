# XID と論文 CORE の小規模回路での性能比較

実施日: 2026-10-05。`feature/paper-core` の同一 `main_release` を使用。
CORE は完全モデルから直接 core 抽出＋削除による極小化を実行し、XID は呼ばない。
本体のソースはこの測定に際して変更していない。

## 条件

- 縮退故障（SAF）、故障リスト省略で全代表故障、limit なしで完全列挙。
- 両方式で `MDC_NODOM=1`。支配関係によるキューブ流用を停止し、方式単体を比較。
- 検証・研究フックを除いた環境で実行。CORE 側だけ `PAPER_CORE=1`。
  `PAPER_CORE_VERIFY` と `GT_BDD` は性能測定時には未設定。
  CORE の通常処理に含まれる core 再確認（1 solve/cube）は有効。
- 方式ごとに1回ウォームアップし、測定を7回。方式の実行順を反復ごとに交互に変更。
  全ジョブを直列実行し、同じ仮想 CPU 0 に固定。
- Intel Xeon Platinum 8573C、Linux x86_64 の管理環境。
- 主指標は子プロセスの user+system CPU 時間（`getrusage` 差分）の中央値。
  起動・読込・故障ごとの CNF 構築・ドントケア判定・列挙・BDD・出力を含む全体時間。
  バイナリの SHA-256 と全実測値を生データに保存。
- 正しさ検証は測定後に両方式を別実行し、`GT_BDD=1`。
  CORE の検証実行では `PAPER_CORE_VERIFY=1` も使用。これらは時間集計から除外。

## 結果

CPU 秒。倍率は CORE / XID で、1未満なら CORE の時間が短い。
キューブ数は全代表故障の `cube_cnt` の総和。全7回で各方式のキューブ数は同一。

| 回路 | 代表故障数 | XID CPU秒 | CORE CPU秒 | 時間倍率 | XID キューブ | CORE キューブ | キューブ削減 |
|---|---:|---:|---:|---:|---:|---:|---:|
| c17a | 22 | 0.009924 | 0.012541 | 1.264 | 65 | 53 | 18.5% |
| s27_C | 32 | 0.011422 | 0.018180 | 1.592 | 104 | 104 | 0.0% |
| s208_C | 215 | 0.442753 | 0.410205 | 0.926 | 10,163 | 1,272 | 87.5% |
| s298_C | 308 | 0.313842 | 0.496521 | 1.582 | 1,578 | 1,115 | 29.3% |

全回路・全反復で両方式の FDP が一致し、代表故障は全て `complete=1`。
別実行の独立 BDD 検証は8ケース全て `ALL VERIFIED`。
等価故障のエコー行は `complete` が空欄であり、代表故障数・キューブ数集計から除外する。

s208_C はキューブが約8分の1になり、CPU 時間の中央値は約7%短い。
ただし XID の7回の範囲は0.432336～0.466453秒、CORE は0.389551～0.483391秒で重なる。
この測定だけで小さな速度差を強い改善と判断しない。
s298_C はキューブが約29%減っても、全体の CPU 時間は約1.58倍。
c17a と s27_C は実行が非常に短いため、数ミリ秒の固定費・ばらつきの影響が大きい。
今回の4回路では、キューブ削減がそのまま全体の高速化につながるわけではなかった。

## 時間の内訳

アプリの既存ログが出す CPU 時間の各7回の中央値。ログの分解能は0.001秒。
0.000は計測桁以下であり、処理が無いという意味ではない。
CaDiCaL は生成側の solve、ドントケアには CORE の否定側 SAT クエリが含まれる。
否定側 oracle の構築や読込等はこれらの区間外にあるため、合計は全体時間と一致しない。

| 回路・方式 | 生成側 SAT秒 | ドントケア秒 | BDD秒 |
|---|---:|---:|---:|
| c17a / XID | 0.000 | 0.000 | 0.000 |
| c17a / CORE | 0.000 | 0.001 | 0.000 |
| s27_C / XID | 0.001 | 0.000 | 0.001 |
| s27_C / CORE | 0.001 | 0.003 | 0.001 |
| s208_C / XID | 0.136 | 0.119 | 0.099 |
| s208_C / CORE | 0.062 | 0.208 | 0.014 |
| s298_C / XID | 0.136 | 0.041 | 0.016 |
| s298_C / CORE | 0.097 | 0.182 | 0.015 |

s208_C では、CORE のドントケア処理は0.119→0.208秒と増えるが、生成側 SAT は
0.136→0.062秒、BDD は0.099→0.014秒に減る。
s298_C ではドントケア処理が0.041→0.182秒に増え、生成側 SAT の短縮0.136→0.097秒を上回る。

## 再現と生データ

```bash
# リポジトリルートで実行。既存の実験出力は上書きしない。
python3 verification/paper_core/benchmark.py
# 回数や回路を変更する例
python3 verification/paper_core/benchmark.py --repeats 7 s208_C s298_C
```

今回の生データ: `output/paper_core_benchmark/20261005T122952Z/`

- `measurements.csv`: 全56回の実測値（ウォームアップ・正しさ検証を除く）。
- `summary.csv`: 各方式・各回路の中央値と CPU 時間の最小・最大。
- `metadata.json`: ビルド識別、固定 CPU、測定条件。
- 回路・方式・反復ごとの `.set` / `.csv` / `.log` / `.stderr`。

`wall_s` も保存するが、Python のプロセス起動・timeout 付き wait の待機間隔を含む。
特に小回路ではこれが相対的に大きいため、上の比較は CPU 時間で行った。
流用ありの既定条件・中大規模回路・遷移故障・低消費電力制約については今回測定していない。


## 設定ファイルでの指定への対応

実装の設定経路を追加した後、再現スクリプト `benchmark.py` は `.set` 内の
`-dc_method xid|core`、`-dom_reuse off`、`-core_verify off` で条件を指定するよう変更した。
正しさ検証時は CORE の `.set` だけ `-core_verify on` にする。
上記の測定値は変更前バイナリの記録であり、生データの SHA-256 で識別できる。
CORE/XID のアルゴリズム自体は変更していない。
Python を使わず `.set` とシェルで実行する場合は `SUMMARY.md` の設定例を参照。
