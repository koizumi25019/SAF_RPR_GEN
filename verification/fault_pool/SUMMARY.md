# verificationの故障ごとの常駐プロセス並列化

## 方式の再検討

同じ故障処理を、回路・代表故障・正常CNFの準備後に作る常駐プロセスへ動的に配分する。
今回の対象はLinux/WSL2などforkを使えるPOSIX環境。baselineには適用していない。

| 候補 | 判断 |
|---|---|
| 常駐プロセス | 採用。CNF・XID・CORE・BDDの可変状態をプロセスごとに隔離し、既存処理を再利用できる |
| 明示的なワーカー構造体を持つスレッド | 将来の候補。CNF、EA、XID、範囲限定、実験フックを全て状態分離する必要があり、現時点で速いという実測はない |
| CNF生成だけをロックするスレッド | XIDと実験フックにも競合が残り、CNF準備の順番待ちも増える |
| 外部バッチ実行 | 実証済みだが、各バッチで回路読込・代表化を繰り返す。今回は一度の準備を継承する |
| 一つのSATソルバを複数故障で共有 | 故障モデルと禁止節の分離・求解の同期が必要。独立故障の同時処理には各ソルバを持つ方式が適する |

この選択は改修範囲と既存実測に基づく。スレッド方式との直接速度比較はしていない。
将来メモリやIPCが律速した場合は、可変フィールドの分離やスレッド化を再評価する。

## 実装

- 親で回路・故障代表化・正常CNF・電力定義を一度だけ準備する。
- 正常CNFの作成後にforkし、各ワーカーがSATソルバ・XID作業領域・BDD managerを持つ。
  読み取り専用ページはcopy-on-writeで共有され、書き込みページは各プロセスへ分離される。
- `AnalyzeOneFault()`を直列・並列の共通処理にする。CNFの各ゲート生成関数は変更しない。
  1故障のCNF→SAT→XID/CORE→禁止節→FDPを一つのワーカーで完結させる。
- 正常CNF範囲限定もワーカー内で行う。検出集合・全PI・FDP分母は維持する。
- 流用なしでは代表故障を一度だけ安定整列する。順序は従来の`SetTarget()`と同じ、
  レベル昇順＋同レベルは元のハッシュ走査順。反復全走査を避ける。
- 空いたワーカーに次の故障IDを1件送る。回路やキューブ・BDDノードは転送しない。
  結果のCSV行（代表・等価故障）・任意の確率系列・統計だけを返す。
- 親は故障ID順に書き出す。完了順によるCSVの変動、欠落、重複を避ける。
- 流用なしではキューブを各故障の終了時に解放し、別故障のために保持しない。
- CPU時間は親＋全子プロセスの合計。SAT・DC・BDDの内訳もワーカーのCPU時間を合計する。
  経過時間と区別する。`Fault Workers`には実際に作ったワーカー数を記録する。
- GTは各ワーカーで独立検証し、親が全件の集計を一度だけ表示する。
  不一致、未知のSAT結果、ワーカー異常終了、書き込み失敗は非ゼロ終了とする。
  従来mainの`RETCODE_ERROR=false`による終了コード0も修正した。
- Ctrl+C/SIGTERMやワーカー障害では、親が残りのワーカーを終了させ、全てwaitする。
  失敗出力は部分結果であり、正常完了ログは出さない。

## 使用方法

`.set`またはCLIに`-jobs N`（1..256、既定1）を指定する。`-set`の後にも指定できる。
複数ワーカーでは流用指定の省略時もoffになり、明示的な`-dom_reuse on`はエラー。
`-jobs 1`は従来の直列で、明示的に指定した流用onも使える。
故障数がNより少なければワーカー数を故障数まで減らす。

検証用ブランチの正常CNF範囲限定は引き続き既定offなので、併用時は明示する。
例えば、リポジトリのルートから次を実行する。

```bash
mkdir -p output/paper_core/limit30/xid/{fdp,log}
cd build
FDP_NORMAL_SCOPE=1 ./main_release -set ../input/script/s5378_C_xid_l30.set -jobs 4
```

COREも`-dc_method core`で同じ構成を利用する。今回はCOREの極小化アルゴリズムを変更していない。
SAF/XID、SAF/CORE、TDF/XID、TDF/CORE、TDF/CORE低電力、`-cube_analysis`、GT検証を対象にする。
COREの詳細統計や通常の範囲限定診断はワーカーごとの表示。

共有ファイルを使う、または並列回帰未実施の研究フックは複数ワーカー時に拒否する。
`AIG_DUMP/AIG_DUMP_DIR/DUMP_CNF/XID_EXTERNAL/CUBE_TREND_CSV/MAXDC/MAXHAM/DUAL/SPLIT/PCOUNT/BDD_EXACT/GT_ISOP`。
これらは`-jobs 1`で従来どおり使える。

## 再現と検証

通常は既存のsetup/CMakeビルドを使う。CMakeがない環境でも、既存の外部ライブラリを使って
次のスクリプトからDebug/Releaseと適用前`476f8ba`の参照Releaseを同じ設定で作れる。
外部ライブラリが別ディレクトリにある場合は`FDP_EXTERNAL_DIR`で指定する。

```bash
python3 verification/fault_pool/build.py
python3 verification/fault_pool/check.py --phase smoke
python3 verification/fault_pool/check.py --phase large
python3 verification/fault_pool/check.py --phase benchmark
```

`results/smoke.json`は小回路、CORE、TDF、低電力、直列互換、出力系列、故障数の少ないケース、
設定エラー、実ワーカーのSIGKILL、親のSIGTERM、書き込み失敗の確認を記録する。
小回路は適用前・直列・並列のCSVを行順も含めバイト比較し、c17aの既知FDPも確認する。
GT_BDDは元の回路から独立に検出集合を構築する検証専用の経路であり、解法のフォールバックではない。

`results/large.json`はs5378_C全4,551代表故障・limit30での直列／並列CSV一致と独立GT検証。
`results/benchmark.json`はGT・内部値照合を無効にした1/2/4/8ワーカー各1回の測定。
各測定は順番に実行し、ビルドや検証を並行しない。

30キューブ上限で未完了になった故障のFDPは下界であり、並列化は一故障の列挙量を減らさない。
fullで一故障だけが極端に重い場合、故障間の並列化だけではその待ち時間を短縮できない。
大回路のメモリ使用量、CORE/TDFの大回路速度、ネイティブWindowsは今回の評価に含めない。

## 2026-10-07の検証・計測結果

小回路9件で、適用前・直列・4ワーカーのCSVが等価故障行と行順も含め完全一致。
c17aの既知FDPとDebug/Releaseも一致。CORE、TDF、低電力、limit2の部分被覆と確率系列、
直列の流用on/off、少数／空の故障リスト、不正設定、共有ファイルフックの拒否を確認した。
実ワーカーのSIGKILLと親のSIGTERMで、非ゼロ終了・全子回収・成功ログなしを確認した。
書き込み失敗も非ゼロ終了。結果は`results/smoke.json`。

s5378_C・limit30は直列／4ワーカーの双方で全4,551代表故障を独立GT検証。
UNSOUND=0、complete-but-NOT-exact=0、完了1,572件。CSVは全バイト一致。
GTは検証のみに使用し、次の性能測定では無効。

正常CNF限定on・SAF/XID・流用off・Release・全4,551代表故障・limit30。
同一クラウド環境（CPUクォータ2コア相当）、各条件1回で中央値ではない。

| ワーカー数 | 経過時間 | 合計CPU時間 | 直列比 |
|---|---:|---:|---:|
| 1 | 47.407秒 | 47.386秒 | 1.00倍 |
| 2 | 27.866秒 | 55.211秒 | 1.70倍 |
| 4 | 33.754秒 | 67.400秒 | 1.40倍 |
| 8 | 34.092秒 | 68.060秒 | 1.39倍 |

全1/2/4/8条件でCSVは完全一致。完了故障数も全て1,572件。
この環境では2ワーカーが最速。4/8では合計CPU時間も増加しており、
ワーカー数を増やすだけでCPU枠を超える倍率は得られない。WSL上の実機の速度は別途測定する。
親で読む回路・故障・正常CNFは一度だけで、起動・通信・出力・終了待ちも経過時間に含む。
生値・実行バイナリSHA256・CPUクォータは`results/benchmark.json`。

## 可読性の整理

並列化の入口と、親の起動・配分・受信・順序付き出力・終了処理を役割別の関数に分離。
通信データ・親の管理状態・子の作業領域の名前と所有権を明示し、日本語コメントを追加した。
回収済みPIDは親の管理情報から消す。故障配分・計算手法・出力形式は維持する。
レビュー時に読む順序と処理図は[REVIEW.md](REVIEW.md)、
整理後の検証結果は`results/regression.json`。
